## INF-01. CI Secret Injection

### Problem Statement

Builds fail without `Secrets.xcconfig` present in the repository. This file is `.gitignore`'d (correctly — it contains credentials), but there is no mechanism to generate it during CI runs. Every GitHub Actions build that touches Supabase configuration will fail.

**File:** `.github/workflows/ios-build.yml`, `.github/workflows/ios-tests.yml`

### Impact

- **Severity:** All CI builds fail — no automated quality gate
- **Scope:** ios-build and ios-tests workflows are non-functional for any code path importing `AppConfig`
- **Consequence:** PRs cannot be validated automatically; developers must trust local builds

### Solution Design

Add a workflow step that generates `Secrets.xcconfig` from GitHub repository secrets before the build step. Add a build-phase script that validates the injected values aren't placeholder strings.

#### Generated File Format

```xcconfig
// Auto-generated by CI — do not commit
SUPABASE_URL = https://xxxx.supabase.co
SUPABASE_ANON_KEY = eyJhbGciOiJIUzI1NiIs...
```

#### Validation Script (Build Phase)

```bash
#!/bin/bash
set -euo pipefail

XCCONFIG="${SRCROOT}/Secrets.xcconfig"

if [[ ! -f "$XCCONFIG" ]]; then
  echo "error: Secrets.xcconfig not found. See README for setup."
  exit 1
fi

while IFS='=' read -r key value; do
  key=$(echo "$key" | xargs)
  value=$(echo "$value" | xargs)
  [[ -z "$key" || "$key" == //* ]] && continue
  if [[ "$value" == "YOUR_"* || "$value" == "PLACEHOLDER"* || -z "$value" ]]; then
    echo "error: $key has a placeholder value in Secrets.xcconfig"
    exit 1
  fi
done < "$XCCONFIG"
```

### Implementation Steps

1. Add GitHub repository secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY`
2. Add step to `ios-build.yml` before "Resolve packages":
   ```yaml
   - name: Generate Secrets.xcconfig
     run: |
       cat > RNF/Secrets.xcconfig << EOF
       // Auto-generated by CI
       SUPABASE_URL = ${{ secrets.SUPABASE_URL }}
       SUPABASE_ANON_KEY = ${{ secrets.SUPABASE_ANON_KEY }}
       EOF
   ```
3. Add identical step to `ios-tests.yml`
4. Add Run Script build phase in Xcode: "Validate Secrets" (before Compile Sources)
5. Ensure `Secrets.xcconfig` remains in `.gitignore`

### Acceptance Criteria

- [ ] `ios-build.yml` passes on CI without manual Secrets.xcconfig
- [ ] `ios-tests.yml` passes on CI without manual Secrets.xcconfig
- [ ] Build fails with clear error if secrets contain placeholder values
- [ ] Secrets.xcconfig is never committed to the repository
- [ ] Local development workflow unchanged (developer creates file manually)

## INF-02. Release Pipeline (TestFlight + App Store)

### Problem Statement

There is no automated path from committed code to users' phones. Every release requires manual Xcode archive, export, and upload — a process that is error-prone, time-consuming, and undocumented.

### Impact

- **Severity:** Blocks continuous delivery — releases take 30+ minutes of manual work
- **Scope:** All releases to TestFlight and App Store
- **Consequence:** Slow iteration, risk of signing mistakes, no audit trail

### Solution Design

New `ios-deploy.yml` workflow using Fastlane for signing, building, and uploading.

#### Trigger Conditions

| Trigger | Target |
|---------|--------|
| Tag push `v*` on `main` | Production → App Store Connect |
| Manual dispatch on `develop` | Staging → TestFlight (internal) |
| Manual dispatch on `main` | Production → TestFlight (external) |

#### Pipeline Steps

1. Checkout code
2. Generate `Secrets.xcconfig` (production values)
3. Install Fastlane and dependencies
4. Resolve signing via `match` (read-only)
5. Increment build number (`github.run_number`)
6. Set marketing version from git tag
7. Build archive via `gym`
8. Export IPA
9. Upload to TestFlight via `pilot`
10. Post Slack/Discord notification with build URL

#### Fastlane Configuration

**Matchfile:**
```ruby
git_url("https://github.com/org/rnf-certificates")
storage_mode("git")
type("appstore")
app_identifier("com.rnf.app")
```

**Gymfile:**
```ruby
scheme("RNF-Production")
export_method("app-store")
output_directory("./build")
derived_data_path("/tmp/RNFDerivedData")
```

**Fastfile:**
```ruby
default_platform(:ios)

platform :ios do
  desc "Deploy to TestFlight"
  lane :beta do
    setup_ci
    match(type: "appstore", readonly: true)
    increment_build_number(build_number: ENV["BUILD_NUMBER"])
    gym
    pilot(skip_waiting_for_build_processing: true)
  end

  desc "Deploy to App Store"
  lane :release do
    setup_ci
    match(type: "appstore", readonly: true)
    increment_build_number(build_number: ENV["BUILD_NUMBER"])
    set_marketing_version(version: ENV["MARKETING_VERSION"])
    gym
    deliver(
      submit_for_review: false,
      automatic_release: false,
      skip_metadata: true,
      skip_screenshots: true
    )
  end
end
```

### Implementation Steps

1. Create certificates repository for `match`
2. Run `fastlane match init` and `fastlane match appstore` locally once
3. Add GitHub secrets: `MATCH_PASSWORD`, `MATCH_GIT_PRIVATE_KEY`, `APP_STORE_CONNECT_API_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `APP_STORE_CONNECT_API_KEY`
4. Create `fastlane/` directory with Matchfile, Gymfile, Fastfile, Appfile
5. Create `.github/workflows/ios-deploy.yml`
6. Add build schemes: `RNF-Staging`, `RNF-Production`
7. Test with manual dispatch to TestFlight staging
8. Verify tag-triggered production deploy

### Acceptance Criteria

- [ ] Tag push `v1.0.0` triggers automated TestFlight upload
- [ ] Manual dispatch deploys staging build to internal TestFlight
- [ ] Build number auto-increments (never conflicts)
- [ ] Marketing version matches git tag
- [ ] Signing resolved automatically via match (no manual provisioning)
- [ ] Failed builds produce actionable error in workflow logs
- [ ] Notification sent on successful upload

## INF-03. Version Automation

### Problem Statement

`CURRENT_PROJECT_VERSION=1` and `MARKETING_VERSION=1.0` are static values in the Xcode project. Every build submitted to App Store Connect requires a unique build number. Marketing versions must follow semver for user-facing updates. Currently both require manual editing.

### Impact

- **Severity:** Blocks automated releases — duplicate build numbers rejected by Apple
- **Scope:** Every release attempt
- **Consequence:** Manual version bumps are forgotten, causing upload failures and wasted CI minutes

### Solution Design

| Version Type | Source | Mechanism |
|-------------|--------|-----------|
| Build number (`CFBundleVersion`) | `github.run_number` | Auto-incrementing per workflow run |
| Marketing version (`CFBundleShortVersionString`) | Git tag (e.g., `v1.2.0`) | Extracted and set during deploy |

#### Build Number Strategy

`github.run_number` is monotonically increasing per workflow, guaranteed unique by GitHub. It resets if the workflow file is renamed, so the workflow should use a stable filename.

#### Marketing Version Strategy

- Tags follow semver: `v1.0.0`, `v1.1.0`, `v2.0.0`
- Deploy workflow extracts version: `echo "${GITHUB_REF#refs/tags/v}"`
- For non-tag deploys (manual dispatch), use latest tag or fallback to `1.0.0`

### Implementation Steps

1. Add to deploy workflow:
   ```yaml
   - name: Set version numbers
     run: |
       BUILD_NUMBER=${{ github.run_number }}
       if [[ "$GITHUB_REF" == refs/tags/v* ]]; then
         MARKETING_VERSION="${GITHUB_REF#refs/tags/v}"
       else
         MARKETING_VERSION=$(git describe --tags --abbrev=0 2>/dev/null | sed 's/^v//' || echo "1.0.0")
       fi
       echo "BUILD_NUMBER=$BUILD_NUMBER" >> $GITHUB_ENV
       echo "MARKETING_VERSION=$MARKETING_VERSION" >> $GITHUB_ENV
   ```
2. Pass to Fastlane: `BUILD_NUMBER` and `MARKETING_VERSION` env vars
3. Fastlane uses `increment_build_number` and `set_marketing_version`
4. Remove static version values from project.pbxproj (replace with `$(MARKETING_VERSION)` and `$(CURRENT_PROJECT_VERSION)` if using xcconfig)

### Acceptance Criteria

- [ ] Build number increments automatically on every CI deploy run
- [ ] Marketing version matches the pushed git tag
- [ ] Non-tag deploys fall back to latest tag version
- [ ] No manual version editing required for releases
- [ ] App Store Connect never rejects for duplicate build number

## INF-04. SPM Package Caching

### Problem Statement

Every CI build resolves Swift packages fresh from the network. This adds 2-5 minutes to every workflow run, wastes bandwidth, and introduces flakiness when package registries are slow or unavailable.

### Impact

- **Severity:** Medium — CI is slower and less reliable than necessary
- **Scope:** `ios-build.yml` and `ios-tests.yml` (every PR and push)
- **Consequence:** ~4 min wasted per run × ~20 runs/day = 80 min/day of CI idle time

### Solution Design

Use `actions/cache` with a key derived from `Package.resolved` hash. On cache hit, skip network resolution entirely.

#### Cache Configuration

```yaml
- name: Cache Swift packages
  uses: actions/cache@v4
  with:
    path: |
      /tmp/RNFDerivedData/SourcePackages
      .build/
    key: spm-${{ runner.os }}-${{ hashFiles('**/Package.resolved') }}
    restore-keys: |
      spm-${{ runner.os }}-
```

#### Cache Invalidation

- Key changes when `Package.resolved` changes (dependency added/updated/removed)
- `restore-keys` fallback allows partial cache hits from previous resolves
- Cache automatically expires per GitHub's 7-day inactivity policy

### Implementation Steps

1. Add cache step to `ios-build.yml` before "Resolve packages"
2. Add identical cache step to `ios-tests.yml`
3. Update `xcodebuild -resolvePackageDependencies` to use consistent `-clonedSourcePackagesDirPath`
4. Verify cache hit on second run with unchanged Package.resolved
5. Verify cache miss and fresh resolve after dependency update

### Acceptance Criteria

- [ ] Second consecutive CI run shows "Cache restored" in logs
- [ ] Package resolution step completes in <30s on cache hit (vs 2-5min fresh)
- [ ] Cache invalidates correctly when Package.resolved changes
- [ ] No stale package issues after dependency updates
- [ ] Both ios-build and ios-tests workflows benefit from caching

## INF-05. Deep Linking Infrastructure

### Problem Statement

No URL handling exists in the app. Widgets cannot route to specific screens. Push notifications cannot open relevant content. Referral links, social sharing, and external integrations have no entry point.

### Impact

- **Severity:** High — blocks widget interactivity, notification routing, and growth features
- **Scope:** Widgets (P15-WGT), notifications (P10-SVC-07), social sharing (P17), referrals
- **Consequence:** Tapping a widget or notification opens the app to its default state rather than contextual content

### Solution Design

#### URL Scheme (Internal Routing)

```
rnf://habit/{id}
rnf://challenge
rnf://profile
rnf://invite/{code}
rnf://streak
rnf://boss
rnf://quest/{id}
rnf://workout
rnf://read
```

Used by: widgets (`widgetURL`), notifications (`userInfo`), internal navigation.

#### Universal Links (External Sharing)

```
https://rnf.app/invite/{code}
https://rnf.app/challenge/{id}
https://rnf.app/profile/{username}
```

Requires: Associated Domains entitlement, AASA file hosted at `rnf.app/.well-known/apple-app-site-association`.

#### DeepLinkRouter Architecture

```swift
// Navigation/DeepLinkRouter.swift
struct DeepLinkRouter {
    enum Route {
        case habit(id: String)
        case challenge
        case profile
        case invite(code: String)
        case streak
        case boss
        case quest(id: String)
        case workout
        case read
    }

    static func parse(url: URL) -> Route? {
        guard let components = URLComponents(url: url, resolvingAgainstBaseURL: true) else {
            return nil
        }

        let pathComponents = components.path
            .split(separator: "/")
            .map(String.init)

        switch (components.scheme, pathComponents.first) {
        case ("rnf", "habit"):
            return pathComponents.dropFirst().first.map { .habit(id: $0) }
        case ("rnf", "challenge"):
            return .challenge
        case ("rnf", "invite"):
            return pathComponents.dropFirst().first.map { .invite(code: $0) }
        // ... additional routes
        default:
            return nil
        }
    }
}
```

#### Integration Points

```swift
// RNFApp.swift
@main
struct RNFApp: App {
    var body: some Scene {
        WindowGroup {
            RootView()
                .onOpenURL { url in
                    if let route = DeepLinkRouter.parse(url: url) {
                        appStateManager.navigate(to: route)
                    }
                }
        }
    }
}
```

### Implementation Steps

1. Add `rnf` URL scheme to Info.plist (`CFBundleURLSchemes`)
2. Add Associated Domains entitlement: `applinks:rnf.app`
3. Create `Navigation/DeepLinkRouter.swift` with route parsing
4. Add `navigate(to:)` method to `AppStateManager` for route handling
5. Wire `.onOpenURL` in `RNFApp.swift`
6. Update widget views to use `widgetURL(URL(string: "rnf://...")!)`
7. Update notification payloads to include `deep_link` key
8. Host AASA file at `rnf.app/.well-known/apple-app-site-association`
9. Test all routes via `xcrun simctl openurl`

### Acceptance Criteria

- [ ] `xcrun simctl openurl booted "rnf://habit/123"` navigates to habit detail
- [ ] `xcrun simctl openurl booted "rnf://challenge"` navigates to challenge screen
- [ ] Widget tap routes to the correct screen
- [ ] Notification tap routes to contextual content
- [ ] Universal link from Safari opens app to correct screen
- [ ] Invalid URLs are handled gracefully (no crash, falls back to home)
- [ ] All routes documented with examples

## INF-06. Crash Reporting

### Problem Statement

No visibility into production crashes. When users experience issues, the only signal is App Store crash reports (delayed 24-48h, minimal context). There is no way to correlate crashes with user actions, app state, or specific builds.

### Impact

- **Severity:** High — blind to production stability
- **Scope:** All production users
- **Consequence:** Crashes go undetected for days, no ability to prioritize fixes by frequency or severity

### Solution Design

Integrate Sentry iOS SDK (preferred over Firebase Crashlytics for: better SwiftUI support, source context in stack traces, performance monitoring, and no Google dependency).

#### Architecture

```
┌─────────────────────────────────────┐
│          SentryService              │
│  (Services/SentryService.swift)     │
├─────────────────────────────────────┤
│  • initialize(dsn:environment:)     │
│  • addBreadcrumb(category:message:) │
│  • setUser(id:tier:version:)        │
│  • captureError(_:context:)         │
└─────────────────────────────────────┘
         │
         ▼
┌─────────────────────────────────────┐
│       Sentry iOS SDK (SPM)          │
│  • Crash capture (signal + mach)    │
│  • dSYM symbolication               │
│  • Breadcrumb trail                  │
│  • User context attachment           │
└─────────────────────────────────────┘
```

#### Breadcrumb Strategy

| Category | Events |
|----------|--------|
| navigation | Screen transitions (tab changes, sheet presentations) |
| service | Supabase calls (method, table, duration) |
| state | Level-up, streak change, challenge advance |
| user-action | Habit completion, workout start/stop, reading upload |

#### User Context (Privacy-Safe)

```swift
SentrySDK.setUser(User(
    userId: SHA256(actualUserId).prefix(16),  // Hashed, not raw
    segment: subscriptionTier.rawValue,       // "free" | "premium"
    other: ["app_version": appVersion, "build": buildNumber]
))
```

**Privacy rules:**
- No PII (name, email, phone) in crash reports
- User ID is hashed (one-way, non-reversible)
- No file paths containing usernames
- Breadcrumbs contain only category + generic message

#### dSYM Upload

Add to release workflow after archive:
```yaml
- name: Upload dSYMs to Sentry
  run: |
    sentry-cli upload-dif --org rnf --project ios ./build/RNF.xcarchive/dSYMs
  env:
    SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}
```

### Implementation Steps

1. Add Sentry SPM dependency: `https://github.com/getsentry/sentry-cocoa` (pinned version)
2. Create `Services/SentryService.swift` wrapper
3. Initialize in `RNFApp.init()` with DSN from xcconfig
4. Add breadcrumbs to: navigation transitions, service calls, state changes
5. Set user context after auth (hashed ID only)
6. Add dSYM upload step to `ios-deploy.yml`
7. Add `SENTRY_DSN` to Secrets.xcconfig per environment
8. Configure Sentry project alerts: crash-free rate < 99%, new issue spike

### Acceptance Criteria

- [ ] Crashes appear in Sentry dashboard within 60 seconds of occurrence
- [ ] Stack traces are fully symbolicated (file + line number)
- [ ] Breadcrumbs show the 5 most recent user actions before crash
- [ ] User context shows hashed ID and subscription tier (no PII)
- [ ] dSYMs uploaded automatically on every release build
- [ ] Sentry alert fires when crash-free rate drops below 99%
- [ ] No PII present in any crash report (audit verified)

## INF-07. Background Processing

### Problem Statement

No `BGTaskScheduler` registration exists. Widget data becomes stale between app launches. Offline queue never flushes unless the user opens the app. Analytics events batch indefinitely in memory.

### Impact

- **Severity:** Medium — degraded experience for widgets, offline sync, and analytics
- **Scope:** Widget freshness, offline reliability, analytics completeness
- **Consequence:** Widgets show yesterday's data, offline completions lost if app is terminated, analytics gaps

### Solution Design

Register three background tasks with the system scheduler:

| Task Identifier | Type | Frequency | Purpose |
|----------------|------|-----------|---------|
| `com.rnf.refresh` | `BGAppRefreshTask` | ~hourly | Update widget shared data via App Group |
| `com.rnf.sync` | `BGProcessingTask` | When WiFi available | Flush offline queue to Supabase |
| `com.rnf.analytics` | `BGProcessingTask` | ~daily | Batch upload analytics events |

#### Architecture

```swift
// Core/BackgroundTaskManager.swift
final class BackgroundTaskManager {
    static let shared = BackgroundTaskManager()

    func registerAll() {
        BGTaskScheduler.shared.register(
            forTaskWithIdentifier: "com.rnf.refresh",
            using: nil,
            launchHandler: handleRefresh
        )
        BGTaskScheduler.shared.register(
            forTaskWithIdentifier: "com.rnf.sync",
            using: nil,
            launchHandler: handleSync
        )
        BGTaskScheduler.shared.register(
            forTaskWithIdentifier: "com.rnf.analytics",
            using: nil,
            launchHandler: handleAnalytics
        )
    }

    private func handleRefresh(task: BGTask) {
        let refreshTask = task as! BGAppRefreshTask

        // 1. Fetch today's progress from local/Supabase
        // 2. Write to App Group UserDefaults
        // 3. Reload widget timelines
        // 4. Schedule next refresh
        scheduleRefresh()
        refreshTask.setTaskCompleted(success: true)
    }

    private func handleSync(task: BGTask) {
        let processingTask = task as! BGProcessingTask

        // 1. Check offline queue count
        // 2. Flush each item with idempotency key
        // 3. Clear flushed items
        // 4. Schedule next sync
        scheduleSync()
        processingTask.setTaskCompleted(success: true)
    }

    func scheduleRefresh() {
        let request = BGAppRefreshTaskRequest(identifier: "com.rnf.refresh")
        request.earliestBeginDate = Date(timeIntervalSinceNow: 3600) // 1 hour
        try? BGTaskScheduler.shared.submit(request)
    }

    func scheduleSync() {
        let request = BGProcessingTaskRequest(identifier: "com.rnf.sync")
        request.requiresNetworkConnectivity = true
        request.requiresExternalPower = false
        try? BGTaskScheduler.shared.submit(request)
    }
}
```

#### Info.plist Registration

```xml
<key>BGTaskSchedulerPermittedIdentifiers</key>
<array>
    <string>com.rnf.refresh</string>
    <string>com.rnf.sync</string>
    <string>com.rnf.analytics</string>
</array>
```

### Implementation Steps

1. Add `BGTaskSchedulerPermittedIdentifiers` to Info.plist
2. Create `Core/BackgroundTaskManager.swift`
3. Register tasks in `RNFApp.init()` (must be before app finishes launching)
4. Implement `handleRefresh`: read progress, write to App Group, reload WidgetCenter
5. Implement `handleSync`: call `OfflineQueueService.flush()` with WiFi requirement
6. Implement `handleAnalytics`: call `AnalyticsService.uploadBatch()`
7. Schedule initial tasks on app background (`scenePhase == .background`)
8. Add expiration handler to each task for graceful cancellation
9. Test with `e]` Xcode debug command: `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.rnf.refresh"]`

### Acceptance Criteria

- [ ] All three tasks registered without crash on app launch
- [ ] Widget data refreshes within ~1 hour of app backgrounding
- [ ] Offline queue flushes when device connects to WiFi (even if app is backgrounded)
- [ ] Analytics batch uploads complete without data loss
- [ ] Tasks reschedule themselves after completion
- [ ] Expiration handlers prevent watchdog kills
- [ ] Simulated launch via Xcode debugger executes task handler correctly

## INF-08. Environment Separation

### Problem Statement

A single Supabase project serves development, testing, and (future) production. Any development mistake — schema change, bad migration, data deletion — directly affects the production database. There is no safe place to test destructive operations.

### Impact

- **Severity:** Critical — data loss risk in production from development actions
- **Scope:** All database operations, all environments
- **Consequence:** A developer running `supabase db reset` or testing a migration could destroy production user data

### Solution Design

Three fully isolated environments:

| Environment | Supabase | Xcconfig | Build Scheme | Branch |
|------------|----------|----------|-------------|--------|
| Development | Local (`supabase start`) | `Secrets.debug.xcconfig` | RNF-Dev | feature/* |
| Staging | Separate project (staging) | `Secrets.staging.xcconfig` | RNF-Staging | develop |
| Production | Production project | `Secrets.release.xcconfig` | RNF-Production | main |

#### Xcconfig Structure

```
RNF/
├── Secrets.debug.xcconfig      # Local Supabase (localhost:54321)
├── Secrets.staging.xcconfig    # Staging project URL + key
├── Secrets.release.xcconfig    # Production project URL + key
└── Config/
    ├── Debug.xcconfig          # #include "Secrets.debug.xcconfig"
    ├── Staging.xcconfig        # #include "Secrets.staging.xcconfig"
    └── Release.xcconfig        # #include "Secrets.release.xcconfig"
```

#### Build Scheme Mapping

Each scheme sets a different build configuration:

- **RNF-Dev**: Debug configuration → `Secrets.debug.xcconfig`
- **RNF-Staging**: Staging configuration → `Secrets.staging.xcconfig`
- **RNF-Production**: Release configuration → `Secrets.release.xcconfig`

#### AppConfig Resolution

```swift
struct AppConfig {
    static var supabaseURL: String {
        Bundle.main.infoDictionary?["SUPABASE_URL"] as? String ?? ""
    }
    static var supabaseAnonKey: String {
        Bundle.main.infoDictionary?["SUPABASE_ANON_KEY"] as? String ?? ""
    }
    static var environment: String {
        Bundle.main.infoDictionary?["APP_ENVIRONMENT"] as? String ?? "development"
    }
}
```

### Implementation Steps

1. Create second Supabase project for staging (via Supabase dashboard)
2. Create `Secrets.debug.xcconfig` (local: `http://localhost:54321`)
3. Create `Secrets.staging.xcconfig` (staging project credentials)
4. Create `Secrets.release.xcconfig` (production project credentials)
5. Create Config xcconfig files that `#include` the appropriate Secrets file
6. Add `APP_ENVIRONMENT` key to each xcconfig (development/staging/production)
7. Create three Xcode schemes: RNF-Dev, RNF-Staging, RNF-Production
8. Update CI workflows to use appropriate scheme and inject correct secrets
9. Add all `Secrets.*.xcconfig` to `.gitignore`
10. Document local setup in README (copy template, fill local values)

### Acceptance Criteria

- [ ] `RNF-Dev` scheme connects to local Supabase (localhost)
- [ ] `RNF-Staging` scheme connects to staging Supabase project
- [ ] `RNF-Production` scheme connects to production Supabase project
- [ ] No cross-environment data leakage possible
- [ ] CI build workflow uses staging secrets for develop branch
- [ ] CI deploy workflow uses production secrets for main/tag
- [ ] `supabase db reset` on local has zero impact on staging/production
- [ ] All Secrets files are gitignored with template copies committed

## INF-09. Dependabot for Swift Packages

### Problem Statement

The existing `dependabot.yml` only monitors GitHub Actions versions. Swift package dependencies (Supabase SDK, Sentry SDK, etc.) are not tracked. Security patches and breaking changes go unnoticed until a developer manually checks.

**Current config:**
```yaml
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
```

### Impact

- **Severity:** Low-Medium — missed security patches, potential breakage on major updates
- **Scope:** All SPM dependencies (currently: Supabase Swift SDK; future: Sentry, etc.)

## INF-10. Database Migration Deployment

### Problem Statement

`migrations-check.yml` validates migration file ordering and presence of RLS/indexes, but never actually deploys migrations to any environment. Schema changes require manual `supabase db push` from a developer's machine — undocumented, error-prone, and unaudited.

### Impact

- **Severity:** Medium — schema drift between environments, no audit trail
- **Scope:** All database schema changes
- **Consequence:** Production schema may diverge from migration files, deployments are manual and risky

### Solution Design

Add deployment steps triggered by branch merges, with appropriate gates:

| Trigger | Target | Gate |
|---------|--------|------|
| Merge to `develop` | Staging Supabase | Automatic (CI passes) |
| Merge to `main` | Production Supabase | Manual approval required |

#### Workflow: `migrations-deploy.yml`

```yaml
name: Deploy Migrations

on:
  push:
    branches:
      - develop
      - main
    paths:
      - 'supabase/migrations/**'

jobs:
  deploy-staging:
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: supabase/setup-cli@v1
      - name: Deploy to staging
        run: supabase db push --linked
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
          SUPABASE_PROJECT_ID: ${{ secrets.SUPABASE_STAGING_PROJECT_ID }}

  deploy-production:
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production  # Requires manual approval
    steps:
      - uses: actions/checkout@v6
      - uses: supabase/setup-cli@v1
      - name: Deploy to production
        run: supabase db push --linked
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
          SUPABASE_PROJECT_ID: ${{ secrets.SUPABASE_PRODUCTION_PROJECT_ID }}
```

#### Safety Measures

- Production deploys require GitHub Environment approval (configured reviewer)
- Migrations only trigger on file changes in `supabase/migrations/`
- `supabase db push` is additive — it applies only new migrations
- Rollback documented in `P14-MIG-03` (manual, per-migration)

### Implementation Steps

1. Create GitHub Environment "production" with required reviewers
2. Add secrets: `SUPABASE_ACCESS_TOKEN`, `SUPABASE_STAGING_PROJECT_ID`, `SUPABASE_PRODUCTION_PROJECT_ID`
3. Create `.github/workflows/migrations-deploy.yml`
4. Link staging project: update `supabase/config.toml` or use `--project-id` flag
5. Test: merge a new migration to develop, verify it appears in staging dashboard
6. Test: merge to main, verify approval gate blocks until approved
7. Document rollback procedure in case of failed migration

### Acceptance Criteria

- [ ] Merge to develop auto-deploys migrations to staging
- [ ] Merge to main requires manual approval before deploying to production
- [ ] Only runs when `supabase/migrations/` files change
- [ ] Failed migration produces clear error and does not partially apply
- [ ] Deployment logs show which migrations were applied
- [ ] No deployment without passing migration-check first (job dependency)

## INF-11. Code Coverage Reporting

### Problem Statement

No visibility into test coverage trends. Unknown which code paths are tested and which are not. No enforcement of minimum coverage, so coverage can silently degrade as features are added without tests.

### Impact

- **Severity:** Low-Medium — quality risk accumulates invisibly
- **Scope:** All source files in `RNF/` target
- **Consequence:** Untested code paths ship to production, regressions undetected

### Solution Design

Enable code coverage collection in CI test runs, export to lcov format, and upload to Codecov for trend tracking and PR annotations.

#### CI Changes

```yaml
- name: Run unit tests with coverage
  run: |
    xcodebuild \
      -project RNF.xcodeproj \
      -scheme RNF \
      -destination "$SIMULATOR_DESTINATION" \
      -derivedDataPath /tmp/RNFDerivedData \
      -only-testing:RNFTests \
      -enableCodeCoverage YES \
      test

- name: Export coverage to lcov
  run: |
    xcrun llvm-cov export \
      /tmp/RNFDerivedData/Build/Products/Debug-iphonesimulator/RNF.app/RNF \
      -instr-profile=$(find /tmp/RNFDerivedData -name "*.profdata" | head -1) \
      -format=lcov \
      > coverage.lcov

- name: Upload to Codecov
  uses: codecov/codecov-action@v4
  with:
    files: coverage.lcov
    flags: unittests
    fail_ci_if_error: false
    token: ${{ secrets.CODECOV_TOKEN }}
```

#### Coverage Thresholds

| Metric | Minimum | Action |
|--------|---------|--------|
| Overall project | 60% | Warn in PR comment |
| Patch (new code) | 70% | Fail CI if below |
| Critical paths (Services/, Core/) | 75% | Tracked separately |

#### PR Integration

Codecov posts a PR comment showing:
- Overall coverage change (+/- %)
- Files changed with line-by-line annotations
- Patch coverage for new code
- Flag if threshold violated

### Implementation Steps

1. Sign up for Codecov and link repository
2. Add `CODECOV_TOKEN` to GitHub secrets
3. Update `ios-tests.yml` with coverage-enabled test command
4. Add lcov export step after tests
5. Add Codecov upload step
6. Configure `codecov.yml` in repo root with thresholds:
   ```yaml
   coverage:
     status:
       project:
         default:
           target: 60%
       patch:
         default:
           target: 70%
   ```
7. Verify PR comment appears on first coverage-enabled run
8. Establish baseline coverage number

### Acceptance Criteria

- [ ] CI test run collects code coverage data
- [ ] Coverage report uploaded to Codecov after every test run
- [ ] PR comments show coverage diff and patch coverage
- [ ] CI warns (does not fail initially) when overall coverage < 60%
- [ ] CI fails when patch coverage of new code < 70%
- [ ] Coverage trends visible in Codecov dashboard over time
- [ ] No performance degradation from coverage instrumentation (< 10% slower)

## INF-12. Portable Automation Script

### Problem Statement

`rnf_cycle.sh` contains hardcoded paths (`/Users/regosenne/Desktop/Dev/RNF`) making it non-portable across machines, CI environments, or other developer setups. Configuration values (branch names, build timeout, log limits) are scattered throughout the script.

### Impact

- **Severity:** Low — only affects automation script usability
- **Scope:** `rnf_cycle.sh` and any future automation scripts
- **Consequence:** Script fails on any machine except the original developer's, CI cannot reuse it

### Solution Design

#### Path Detection

Replace hardcoded path with dynamic detection:

```bash
#!/bin/bash
set -euo pipefail

# Dynamic root detection — override with RNF_ROOT env var
ROOT_DIR="${RNF_ROOT:-$(cd "$(dirname "$0")/.." && pwd)}"

# Verify we're in the right place
if [[ ! -f "$ROOT_DIR/RNF.xcodeproj/project.pbxproj" ]]; then
    echo "error: Cannot find RNF project at $ROOT_DIR"
    exit 1
fi
```

#### Configuration Extraction

Create `.env.automation` for configurable values:

```bash
# .env.automation — automation configuration
# Copy to .env.automation.local for personal overrides

RNF_SCHEME="RNF"
RNF_BUILD_TIMEOUT=300
RNF_LOG_DIR="logs"
RNF_MAX_LOG_FILES=50
RNF_BRANCH_MAIN="main"
RNF_BRANCH_DEVELOP="develop"
```

#### Script Loading Pattern

```bash
# Load defaults, then local overrides
source "$ROOT_DIR/.env.automation"
[[ -f "$ROOT_DIR/.env.automation.local" ]] && source "$ROOT_DIR/.env.automation.local"
```

#### Log Rotation

Add log rotation to keep last N cycles:

```bash
rotate_logs() {
    local log_dir="$ROOT_DIR/$RNF_LOG_DIR"
    local max_files="${RNF_MAX_LOG_FILES:-50}"
    
    ls -t "$log_dir"/cycle_*.log 2>/dev/null \
        | tail -n +$((max_files + 1)) \
        | xargs -r rm --
}
```

### Implementation Steps

1. Replace all hardcoded paths in `rnf_cycle.sh` with `$ROOT_DIR`
2. Add root detection logic at script top
3. Create `.env.automation` with default configuration values
4. Create `.env.automation.template` (committed) and add `.env.automation.local` to `.gitignore`
5. Add `source` loading of configuration file
6. Add project existence validation after path detection
7. Add log rotation function, called at end of each cycle
8. Test on a different machine / directory to verify portability
9. Update any documentation referencing the old path

### Acceptance Criteria

- [ ] Script runs from any directory without modification
- [ ] `RNF_ROOT` env var override works correctly
- [ ] Script fails with clear error if project not found at detected path
- [ ] All configuration values come from `.env.automation` (no magic numbers in script)
- [ ] `.env.automation.local` overrides work without being committed
- [ ] Log rotation keeps only the last 50 log files
- [ ] Script works in CI environment (no user-specific paths)
